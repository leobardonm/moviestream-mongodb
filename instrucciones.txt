Contexto
Ya conocen MovieStream desde el modelo relacional en Oracle: tablas, llaves foráneas, relaciones N:M resueltas con tablas intermedias, JOINs para reconstruir la información.

En esta actividad van a tomar ese mismo dominio y lo van a llevar al mundo documental con MongoDB. Pero modelar no es suficiente: la mejor manera de saber si un modelo está bien diseñado es construir algo encima de él. Por eso, además del modelo, van a desarrollar una aplicación interfaz web que les permita interactuar con sus datos.

Lo importante no es la app. Lo importante es que al construirla descubran qué tan ergonómico (o doloroso) resultó su modelo. Aunque pueden divertirse haciendo la App como ustedes deseen.

Propósito
Al terminar la actividad, deberás ser capaz de:

Traducir un modelo relacional existente a un modelo documental, justificando cada decisión de diseño
Distinguir cuándo conviene embeber datos y cuándo conviene referenciarlos
Resolver relaciones muchos-a-muchos sin tablas intermedias
Implementar operaciones CRUD básicas contra una base de datos NoSQL
Reflexionar sobre los trade-offs reales que descubriste durante la implementación
Instrucciones
1. Modelo documental de MovieStream
A partir del ERD relacional que ya conoces, propón un modelo equivalente en MongoDB. Para cada relación del modelo original, decide y documenta tu decisión:

¿Embeber o referenciar?
Si referencias, ¿en qué dirección? ¿En ambas?
¿Cuántas colecciones quedan al final?
¿Qué consultas se vuelven más fáciles? ¿Cuáles más difíciles?
Entrega este modelo como un archivo MODEL.md dentro de tu repositorio, donde muestres la estructura propuesta de cada colección (puede ser con ejemplos de documentos JSON) y la justificación de cada decisión en lenguaje claro.

2. Base de datos poblada en MongoDB
Crea la base de datos en MongoDB (puede ser local o MongoDB Atlas, lo que prefieras) y cárgala con datos de prueba que reflejen el dominio: al menos 20 películas, 5 géneros, 10 actores y 15 usuarios con interacciones (vistas, ratings, lo que apliques según tu modelo).

Los datos no tienen que ser reales, pero sí coherentes — que las relaciones tengan sentido y permitan probar las operaciones.

Incluye en el repositorio un script (seed.js, seed.py o similar) que pueda recrear la base desde cero. Si yo clono tu proyecto, debería poder correr ese script y tener tu BD lista para probar.

3. Aplicación web simple
Una interfaz web que permita interactuar con tu base de datos. Sin autenticación, sin manejo de usuarios, sin frontend complejo — el objetivo es que tú toques tus datos y veas tu modelo en acción.

La app debe permitir, sobre al menos dos colecciones distintas de tu modelo:

Listar los documentos (con búsqueda o filtros básicos)
Crear nuevos documentos
Editar documentos existentes
Eliminar documentos
Una de las dos colecciones debe ser la que tenga relaciones con otras (sea por embebido o por referencia), porque ahí es donde aparecen las decisiones interesantes: ¿cómo manejas crear una película con sus géneros?, ¿qué pasa al borrar un género que está siendo referenciado?, ¿cómo muestras los datos relacionados al usuario?

Sobre cómo construirla
Esta parte de la actividad está pensada para que la hagas con apoyo de IA: vibe coding, Claude Code, ChatGPT, Cursor, lo que prefieras. No es trampa, es la realidad del trabajo de software hoy. Lo que sí espero es que entiendas cada decisión técnica y puedas explicarla.

Stack libre. Sugerencias:

Más simple posible: Node.js + Express + plantillas EJS o Pug, conectado a MongoDB con el driver oficial o Mongoose
Si quieres practicar algo moderno: Next.js con MongoDB
Si prefieres Python: Flask + PyMongo
Lo más minimalista: un solo archivo HTML con fetch a una API en Express
No me importa el diseño visual. Me importa que funcione y que el código sea legible.

4. Deployment de la aplicación
La app debe estar publicada y accesible desde una URL pública. No basta con que corra en tu máquina.

Puedes usar el servicio que prefieras, siempre que tenga un tier gratuito y la app sea accesible sin que yo tenga que hacer login en nada. Algunas opciones:

GitHub Pages — si tu app es solo HTML/JS contra una API externa
Vercel — excelente para Next.js, Express, frontend estático
Render — gratis para apps Node/Python, ideal si necesitas un servidor con BD conectada
Railway, Fly.io, Netlify — alternativas válidas
Para la base de datos, MongoDB Atlas tiene un tier gratuito (M0) que conecta directo con cualquiera de estos servicios — esa es la ruta más sencilla.

Verifica que tu URL funcione desde una ventana de incógnito antes de entregar. Si yo abro tu liga y la app no carga, no se evalúa.

 

5. Reporte de reflexión
Un archivo REFLECTION.md (o PDF, como prefieras) con tus respuestas a las preguntas de reflexión que están más abajo. Sin extensión mínima ni máxima — escribe lo que necesites para responder honestamente.

6. README
Tu repositorio debe tener un README.md con:

Qué hace el proyecto
Cómo correrlo desde cero (incluyendo el seeding de datos)
Qué stack usaste y por qué
Una captura de pantalla de la app funcionando
Preguntas de reflexión
Estas preguntas no tienen una respuesta correcta. Lo que busco es que mires hacia atrás en tu proceso y observes qué pasó realmente. Responde con ejemplos concretos de tu propio modelo y código cuando sea posible.

1. Volviendo a empezar. Si tuvieras que rediseñar tu modelo desde cero hoy, ¿qué cambiarías? Piensa en ese momento durante la implementación en el que dijiste "esto debí haberlo hecho diferente". ¿Qué fue, y qué información te faltaba al inicio que solo descubriste cuando empezaste a escribir queries?

2. La conversación con tu modelo. Mientras construías el CRUD, ¿hubo alguna operación que se sintió incómoda o forzada? ¿Una donde tuviste que hacer dos o tres queries para algo que en SQL hubiera sido un JOIN trivial? Descríbela. ¿Crees que ese dolor era inherente a NoSQL, o era una consecuencia de cómo modelaste tú?

3. La pregunta honesta. Para el dominio de MovieStream específicamente — no para "aplicaciones modernas" en abstracto — ¿realmente NoSQL fue mejor opción que el modelo relacional original? Argumenta tu respuesta tomando en cuenta tu experiencia construyendo la app, no lo que dice la teoría. Si tu respuesta es "depende", explica de qué.
